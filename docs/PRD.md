## 1. 执行摘要

### 1.1 一句话

**AcouAgent 是一个用自然语言驱动的声学仿真智能体——用户像和人对话一样描述声学问题，系统自动完成仿真并给出可视化的、可解释的结论。**

### 1.2 它是什么

AcouAgent 是一款 **Web 对话式声学仿真工具**。底层基于 jwave 声学求解器 + LLM 智能体，用户不需要写一行代码，不需要配置仿真环境，不需要了解数值方法。

**产出**：一个可访问的 Web 应用（对话界面），用户输入自然语言，获得：

- 📊 压力场热力图（PNG）
- 📈 传感器波形图（PNG）
- 📋 关键物理量摘要（峰值压力、RMS、衰减）
- 💡 自然语言仿真结论与物理含义解读

### 1.3 解决什么问题

今天要做一次声学仿真，典型流程是：配环境 → 写 Python → 调 jwave API → 跑仿真 → 看原始数组 → 自己画图 → 自己分析。整个过程耗时数小时到数天，且门槛极高（需要会 Python、懂 jwave、懂数值方法）。

AcouAgent 把这件事压缩到**一次对话，3 分钟内**。

### 1.4 当前状态

已有可工作的后端：Dify 工作流 + jwave 沙箱执行 + LLM 自动纠错。34 次端到端测试，成功率 76%。当前缺失的是**前端产品层**（用户现在面对的是 Dify 原生聊天界面 + 原始 stdout 输出）。

### 1.5 核心差异化

| | 传统仿真工具 (COMSOL/Matlab) | jwave 直接使用 | **AcouAgent** |
|---|---|---|---|
| 交互方式 | GUI 菜单 + 手动配置 | 写 Python 代码 | **自然语言对话** |
| 上手时间 | 数周 | 数天 | **零** |
| 需要编程 | 部分需要 | 必须 | **不需要** |
| 结果解释 | 用户自行分析 | 用户自行分析 | **智能体自动解读** |
| 纠错方式 | 报错后手动改 | 看 traceback 改代码 | **自动检测+修正+重试** |
| 仿真迭代 | 手动改参数 | 手动改代码 | **多轮对话增量修改** |

## 2. 市场分析

### 2.1 目标用户

| 用户群 | 规模估算 | 典型场景 | 当前痛点 |
|--------|----------|----------|----------|
| **声学研究者**（核心） | 国内约 5000-10000 人 | 快速验证假设、参数扫描 | 每次改参数要改代码，迭代慢 |
| **医学超声工程师** | 国内约 3000-5000 人 | 超声场分布、组织衰减研究 | 多数不会 Python，依赖仿真同事 |
| **高校师生** | 每届相关专业约 2000 人 | 教学演示、课题仿真 | 配环境就要一周，弃坑率高 |
| **医疗器械 R&D** | 国内约 200-500 家 | 超声探头设计验证 | 商用软件贵（COMSOL 年费 10 万+） |

### 2.2 竞争格局

| 产品 | 类型 | 价格 | 优势 | 劣势 |
|------|------|------|------|------|
| COMSOL Multiphysics | 商业 GUI | ¥10 万+/年 | 功能全、工业验证 | 贵、重、需要专业培训 |
| k-Wave (MATLAB) | 开源 | 免费 | 学术标准、成熟 | 需要 MATLAB 许可证、需编程 |
| jwave (Python) | 开源 | 免费 | 基于 JAX、GPU 加速 | **API 冷门、LLM 不懂**、需编程 |
| Field II | 开源 | 免费 | 超声换能器标杆 | 仅限换能器仿真、需编程 |
| **AcouAgent** | Web 对话 | 免费（MVP） | **零门槛、对话式、自动纠错** | 功能深度不如 COMSOL |

**市场空白**：开源的 jwave/k-Wave 需要编程能力，商业软件太贵太重。没有一个产品能让不懂编程的人快速上手声学仿真。AcouAgent 填补这个空白。

### 2.3 市场策略

MVP 阶段**不收费**，目标是通过开源社区（GitHub）和学术渠道（声学会议、高校合作）获取早期用户和反馈。P2 后评估商业化路径：SaaS 订阅（云端 GPU 仿真）或企业私有部署。

## 3. 产品定义

### 3.1 产品形态

一个**基于浏览器的对话式 Web 应用**。单人使用，无需注册登录（MVP）。

**MVP 交付物**：一个可通过浏览器访问的 URL，打开后是一个聊天界面。

### 3.2 核心功能（MVP）

| 功能 | 说明 |
|------|------|
| 💬 自然语言对话 | 用户描述声学问题，智能体理解、反问、建议 |
| 🔧 自动方案推荐 | 智能体根据需求推荐仿真参数（维度、网格、介质参数） |
| 📝 自动代码生成 | 将参数转为可执行的 jwave Python 代码 |
| 🏗️ 沙箱执行 + 自动纠错 | Docker 隔离执行，失败自动 LLM 纠错重试（≤7 次） |
| 📊 可视化输出 | 压力场热力图、传感器波形图（PNG） |
| 📋 结果解读 | 关键物理量 + 自然语言结论 |
| 🔄 多轮迭代 | "把频率改成 3MHz"——增量修改，无需重新描述 |
| ⚡ 参数预校验 | Nyquist/CFL/PML 物理约束自动检查 |

### 3.3 不在 MVP 内

3D 仿真、用户注册登录、计费、移动端适配、COMSOL 导入导出、多物理场耦合。

### 3.4 用户看到的是什么

用户打开浏览器，进入一个聊天界面。交互如下：

```
🤖 你好！我是声学仿真智能体。你可以直接描述你想研究的声学问题。

👤 我想仿真 5MHz 超声在含 3mm 囊肿的软组织中传播，
   看看囊肿前后的衰减差异

🤖 好的，我的建议：
   · 2D 仿真，区域 15×15 mm，分辨率 0.1 mm
   · 软组织声速 1540 m/s，密度 1050 kg/m³
   · 囊肿 φ=3mm，圆形，声速 1600 m/s
   · 点源 5MHz，位于区域顶部
   · 在囊肿前后各放置一个虚拟传感器记录波形
   [开始仿真] [修改参数]

👤 [点击开始仿真]

🤖 ⏳ 生成代码 → 运行仿真... ✅ 完成 (12.3s)

   ┌──────────────────────────┐
   │  🔴 压力场 · t=15μs       │
   │  [热力图 - 可见囊肿边界    │
   │   的反射和阴影区]          │
   └──────────────────────────┘

   ┌──────────────────────────┐
   │  📈 传感器 1 (囊肿前)      │
   │  [波形图 - 峰值 620 Pa]    │
   │  📈 传感器 2 (囊肿后)      │
   │  [波形图 - 峰值 89 Pa]     │
   └──────────────────────────┘

   📊 囊肿前峰值 620 Pa，囊肿后峰值 89 Pa，衰减 16.9 dB
   💡 反射系数约 0.14，与理论值量级一致。5MHz 超声穿透
      3mm 囊肿后几乎完全衰减——频率越高，穿透力越弱。
      如需更好的穿透力，可以试试降低频率。

👤 换成 3MHz 试试

🤖 ⏳ ... ✅ (10.1s)  [同上输出 3MHz 结果]
   💡 3MHz 衰减 8.2 dB，远低于 5MHz 的 16.9 dB——
      低频穿透力更强，符合物理预期 ✅
```

## 4. 用户旅程

### 4.1 首次使用

```
发现 AcouAgent (GitHub/论文/同事推荐)
  → 打开浏览器
    → 看到聊天界面
      → 用自然语言描述第一个仿真问题
        → 智能体反问/建议，确认方案
          → 点击"开始"
            → 等待 ∼30 秒
              → 看到热力图 + 波形图 + 自然语言解读
                → 说"换参数再试一次"
                  → 10 秒后拿到对比结果
```

### 4.2 典型使用场景

**场景 1：研究者参数扫描**
"帮我在 1-10MHz 范围内，以 1MHz 步长，仿真超声在软组织中的衰减曲线"
→ 智能体逐一执行，输出对比图

**场景 2：工程师介质对比**
"对比骨骼（3000 m/s）和软组织（1540 m/s）在 2MHz 下的声场差异"
→ 两次仿真，并排对比

**场景 3：教学演示**
"展示 2MHz 超声波在水中传播的波前”——播放各时间步的压力场"

## 5. 产品架构

### 5.1 系统总览

```
用户浏览器 (Web Chat UI)
       │
       ▼
   Dify API (编排层)
       │
       ├──→ LLM (需求分析 → 参数提取 → 代码生成 → 结果解释)
       ├──→ 知识库 (jwave API 参考 + 代码模板 + 物理规则)
       └──→ MCP Server (工具网关)
                │
                ├──→ 参数校验 (物理规则硬编码)
                ├──→ 沙箱执行 + 自动纠错
                └──→ 结果分析 + 可视化生成
                     │
                     ▼
              jwave Executor (Docker 隔离环境)
```

### 5.2 技术选型

| 层 | 技术 | 理由 |
|----|------|------|
| 前端 | Gradio (MVP) → Next.js (P2) | Python 生态一致，开发快 |
| 编排 | Dify 1.16.1 | 已有，工作流 + 对话管理 |
| LLM | DeepSeek (chat/coder/flash) | 性价比高，纠错场景够用 |
| 仿真引擎 | jwave 0.2.1 + JAX CPU | 开源，Python 原生，GPU 可扩展 |
| 沙箱 | Docker + subprocess 双层隔离 | 安全第一 |
| 可视化 | matplotlib (executor 内) | 成熟，PNG 输出直接嵌入聊天 |

## 8. 落地可行性

### 8.1 技术可行性：高

- **后端已跑通**：34 次端到端测试验证了 Dify + MCP + jwave 链路可行
- **核心技术风险可控**：成功率 76% → 90% 的路径清晰（提示词 + 知识库），有明确的改进方向
- **已知依赖**：deepseek API（备选：其他兼容 OpenAI 接口的 LLM）、Dify（备选：自建编排）、jwave 0.2.1（版本锁定）

### 8.2 团队可行性：单人可做

- 核心代码量约 500 行 Python（server_safe.py + executor.py），已有
- Web 前端用 Gradio 约 200 行 Python
- 新增 MCP 工具（参数校验 + 结果分析）约 300 行
- Prompt 工程 + 知识库文档为主要工作量

### 8.3 时间可行性

8 周从当前状态到可发布产品，比从零开始快，因为：
- 后端 80% 已有
- 主要增量工作是前端 + Prompt + 知识库
- 不需要新学技术栈

### 8.4 单人开发的 MVP 策略

所有"可选"的做减法：不做 3D（先让 2D 跑稳）、不做用户系统（单人用）、不做多语言（先中文）、不做 SDK（先对话界面）。只做让第一个用户（你自己）能顺畅使用的东西。

### 附录 A：业务流程与状态机

#### A.1 9 步核心流程

```
用户输入
  → 1. 需求理解（LLM 分析意图，必要时反问）
  → 2. 方案建议（推荐仿真参数，用户确认）
  → 3. 参数提取（结构化 JSON）
  → 4. 参数校验（MCP 硬编码物理规则）
  → 5. 代码生成（LLM + 知识库 + API 黑名单）
  → 6. 沙箱执行 + 自动纠错（Docker + DeepSeek ≤7次重试）
  → 7. 结果分析（提取压力场数据 + 生成 PNG + 合理性检查）
  → 8. 结果审查（LLM 判断：合理 / 需重试 / 失败）
  → 9. 自然语言解释（文字结论 + 图片）
  → 返回用户
```

迭代循环：步骤 8 判断"需重试" → 回到步骤 3（最多 3 次）。

#### A.2 仿真状态机

```
idle → planning → clarifying（需求模糊时）→ awaiting_params
  → validating → generating → executing
  → [成功] analyzing → explaining → completed
  → [失败+retry<7] fixing → executing
  → [失败+retry≥7] failed
  → [迭代<3+异常] refining → awaiting_params
```

| # | 模块 | 职责 | 阶段 |
|---|------|------|------|
| 1 | 对话引擎 | 多轮对话管理、消息路由 | P0 |
| 2 | 需求分析器 | 理解意图、反问、领域知识 | P0 |
| 3 | 参数提取器 | 结构化 JSON 输出 | P0 |
| 4 | 参数校验器 | Nyquist/CFL/PML 硬编码校验 | P1 |
| 5 | 代码生成器 | jwave 代码生成 + API 黑名单 | P0 |
| 6 | 沙箱执行器 | Docker 隔离执行 | P0 |
| 7 | 纠错引擎 | LLM 自动纠错重试 | P0 |
| 8 | 结果分析器 | 数据提取 + PNG 生成 | P1 |
| 9 | 结果解释器 | 自然语言结论 | P1 |
| 10 | 执行看板 | 历史记录、成功率统计 | P2 |

### 附录 B：AI 设计——Prompt、知识库、模型与工具

#### B.1 知识库文档清单

#### B.2 模型职责

| 节点 | 模型 | 温度 | 说明 |
|------|------|------|------|
| 需求分析 | deepseek-v4-flash | 0.7 | 快速、成本低 |
| 参数提取 | deepseek-v4-flash | 0.3 | 结构化输出 |
| 代码生成 | deepseek-coder | 0.1 | 代码质量优先 |

降级策略：coder 不可用 → chat；flash 不可用 → chat；qwen3-rerank 不可用 → 仅向量检索。

#### B.3 Prompt 核心策略

**代码生成 Prompt 关键设计**：嵌入 ✅**正确 API** + ❌**禁止 API 黑名单** + **完整代码模板**。让 LLM 从一开始就写对，而非依赖纠错。

禁止 API 黑名单：
- `p0.shape` → 必须用 `p0.params.shape`
- `time_axis.t` → 必须用 `time_axis.to_array()`
- `FourierSeries.from_array(...)` → 必须用 `FourierSeries(data, domain)`
- `Sources(domain=..., source=...)` → 必须用位置参数

纠错 Prompt 额外注入 jwave 常见错误模式速查表，让纠错 LLM 知道"看到 `has no attribute 'shape'`，应该试 `.params.shape`"。

### 附录 D：30 条 Given-When-Then 验收标准

#### D.1 对话与需求理解 (1-6)

1. **基础仿真请求**：Given 用户输入"仿真 2MHz 超声在水中传播"，When 发送，Then 5 秒内回复含 2D 确认 + 声速 + 分辨率建议 + 反问是否需要异质介质
2. **模糊需求反问**：Given "仿真超声看看效果"，When 发送，Then 反问 ≥2 个澄清问题
3. **完整需求直接执行**：Given 详细描述了 2D 点源仿真需求，When 发送，Then 直接出方案，不反问
4. **多轮增量修改**：Given 刚完成 5MHz 仿真，When "改成 3MHz"，Then 只改 frequency，其余参数复用
5. **介质切换**：Given 刚完成水仿真，When "换成软组织 1540"，Then 更新 sound_speed/density 并重新仿真
6. **诚实告知边界**：Given 用户请求超出能力范围（如飞机发动机噪声），Then 说明能力边界，不编造结果

#### D.2 参数提取与校验 (7-12)

7. **标准参数提取**：Given "2D 水中 5MHz 点源"，Then 输出 JSON 含 sound_speed=1500, frequency=5e6, source_type="point_source"
8. **Nyquist 拦截**：Given dx=1mm, freq=5MHz，Then 校验失败，指出 λ_min=0.3mm，需 dx≤0.075mm
9. **CFL 拦截**：Given cfl=0.5，Then 校验失败，建议改为 ≤0.3
10. **网格下限**：Given Nx=16，Then 校验失败，指出 jwave 需 N≥32
11. **时间过长警告**：Given t_end=1s，Then 警告但允许强制执行
12. **全部通过**：Given 参数合法，Then 返回 valid=true，进入代码生成

#### D.3 代码生成与执行 (13-18)

13. **正确 API**：Given 标准参数，Then 代码用 `time_axis.to_array()` 而非 `.t`，用 `p0.params.shape` 而非 `.shape`
14. **无 markdown**：Given 代码生成完成，Then 不含 \`\`\`python 标记
15. **点源执行成功**：Given 正确 2D 点源代码，Then exit_code=0, max_pressure > 0
16. **API 错误自动修复**：Given 代码含 `p0.shape` 错误，Then 第 1 次失败，DeepSeek 纠正为 `p0.params.shape`，第 2 次成功
17. **markdown 清理**：Given 代码被 \`\`\`python 包裹，Then 自动去标记后成功
18. **超时处理**：Given 死循环代码，Then 30s 后被 killpg，不阻塞后续请求

#### D.4 结果分析 (19-24)

19. **非零检测**：Given stdout 含 max_pressure: 620.5，Then 返回 has_signal=true, verdict=normal
20. **全零检测**：Given max_pressure: 0.0，Then 返回 verdict=zero_field，建议改用 p0 方式
21. **热力图生成**：Given 仿真成功，Then 生成 PNG 热力图（plasma 配色 + 坐标轴 + colorbar）
22. **波形图生成**：Given 有传感器数据，Then 生成时间-压力波形图
23. **物理量准确**：Given 已知数据，Then 峰值/RMS/衰减计算误差 < 1%
24. **维度识别**：Given 2D 结果，Then 生成 2D 热力图而非 1D 曲线

#### D.5 迭代与决策 (25-27)

25. **全零触发重试**：Given pressure_max=0，Then 审查 LLM 输出 retry，建议改用 p0 方式，回到参数提取
26. **3 次放弃**：Given 连续 3 次异常，Then 输出 fail，如实告知用户
27. **正常通过**：Given 结果合理，Then 输出 pass，进入结果解释

#### D.6 结果解释 (28-30)

28. **含关键数值**：Given 仿真完成，Then 输出 ≥3 句，含峰值压力、衰减、物理意义
29. **异常不伪装**：Given 仿真失败，Then 不编造假数值，诚实说明
30. **对比解释**：Given 同 conversation 内两次仿真，Then 第二次输出含与第一次的对比分析
